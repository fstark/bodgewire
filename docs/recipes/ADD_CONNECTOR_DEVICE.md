# Recipe — Add a device behind a Connector

A standard device off the Board, plugged into a Connector Part: the paddle controller (P4i), the ASCII keyboard (P4n). The device's logic lives inside the Connector Part, so it is simulated like a chip; the Board holds only the header. Devices whose arrangement belongs to the Board (LEDs, digits, buttons) are on-board Parts instead: [ADD_BOARD_DEVICE.md](ADD_BOARD_DEVICE.md).

Reference commits (paddle controller): `8bfbcc6` Part, connector pins, footprint, power; `da76381` knob through the Session, `bw run`, `bw_ui`; `d24f490` → `e1468a0` the knob meter Machine (045). Keyboard: `e0feb33` Part (a setting that is an event), `53e109f` typing through the Session, `--type`, a bench netlist, `605db6c` the capture mode in `bw_ui`; `23a4d87` control codes through the Session, `5ef5183` the drawn layout, `785e7a7` the keyboard window (P4o). Matrix keyboard (P5q, `a0d2ab3`): keys as switch contacts, a window, PC typing and paste; the same commit's `MONITOR` (a monitor on separate drives). Passive connectors with the PET's pin labels: `7668c14`.

## The chain

| Layer | File | What |
|---|---|---|
| Part | `src/parts/<device>.{hpp,cpp}` | a `Component` with the connector's pins in pad order (pin index = pad − 1); signal pins TTL `Input`/`Output`, power pins `Power`. The device's behaviour in `evaluate` (`fell`, `wakeAfter`, `drive` with a delay of at least 1 ps). The player's setting is a `std::atomic` written by the UI thread (`Paddle::setKnob`, clamped); a setting read only at the next event needs no wake, unlike a button press. A setting that is an event (a key) goes into a lock-free single-producer queue in the Part (`Keyboard::type`) followed by a wake; a device with no inputs is evaluated only on wakes, so it tells its own wakes from the Session's by time (`nextAt_`). Dropping queued events from the producer side needs a marker the consumer honours (`dropWaiting`), never a reset of the consumer's index |
| Parameters | `src/parts/catalogue.cpp` | `CreateXxx(reference, parameters)` refuses unknown or missing names with a message; an optional one has a default (`reversed=yes\|no`, default `no`); durations by `DurationFromText` (`src/parts/paddle.hpp`: `bw_parts` cannot reach `bw_netlist`'s `ParseDuration`) |
| Catalogue | `src/parts/catalogue.cpp` | `PartInfo` row sorted by name, `PartKind::Connector`, package e.g. `KK-4` |
| Pins | `src/parts/connector.{hpp,cpp}` | `ConnectorPins("<NAME>")`: names and kinds for the electrical netlist |
| Power | `connector.cpp` `ConnectorPowersDevice`, `src/machine/electrical.cpp` `FindPower` | a device fed by the Board is Powered like a chip: unpowered, its pins go on private Nets (`BoardPower::unpowered`). `POWER` and `VIDEO` stay unpowered Connectors |
| Footprint | `src/board/kicad_netlist.cpp` | package → KiCad footprint in `kFootprints` |
| Finder | `src/netlist/builder.{hpp,cpp}` | `XxxOf(loaded, ref)` (`PaddleOf`), for the Session, CLI and tests |
| Manual check | `src/manual/manual.cpp` `PartPinNames` | builds each Part without parameters: give a Part that needs them its own |
| Setting | `src/machine/<x>_setting.{hpp,cpp}` | the CLI text form (`ParseKnob("J2:40%")`) |
| Session | `src/session/session.{hpp,cpp}` | list (`knobs()`), set, get; kept in a map by reference and reapplied after every rebuild (power-on after a Repair) |
| CLI | `src/cli/main.cpp`, `src/ui/main.cpp` | `--knob REF:N%`, applied before power-on; a reference that is not the device is a usage error |
| UI | `src/ui/<device>_window.{hpp,cpp}`, `src/ui/shelf.cpp`, `src/view/bench_places.cpp` | the device as a drawn case on the bench (P6d; `knob_window.cpp`: one box a controller, the knob turned by a vertical drag or the wheel): no title bar, dragged by its body, `PlaceNext` (its `BenchObject`'s default place each time it comes out; on the bench, or popped out in its own desktop window, P6j: every case goes through it), `KeepAspect` (resized from the corner in proportion), `CaseClose` (the × on the case puts it away), all in `src/ui/bench.hpp`; out from its equipment drawing on the shelf (`ToggleWindow` by its window name), the drawing grayed on a Machine without the device (P6c). Its keys work while it is away (`KnobWindow::keys`: Up/Down unless text input has the keyboard). A device with many controls draws them like the real thing (`keyboard_window.cpp`: caps from a layout in `src/view`, tested headless); drawn also without a Board |
| Datasheet | `datasheets/<NAME>.md` | the connector's pins and the device inside |

Tests: `tests/parts/<device>_test.cpp` (row, pins, parameters refused with their messages, behaviour, setting clamped, `ConnectorPowersDevice`), `tests/machine/<x>_setting_test.cpp`, `[session]` cases (setting kept across power, and across a Repair once a Machine has a Puzzle), `manual_test.cpp` (pin names).

## Kinds of device

- **Passive** (a header with nothing plugged in: `IEEE488`, `USERPORT`, `CASSETTE`): `Connector` with every pin a `sampled` MOS `Input` (no "floats high", never woken: an 8 MHz video line on a user port must not evaluate an empty Part every dot); grounds and `VCC` named as the real connector's but plain `Input`s listed on the rails (a `Power` pin named `GND1` needs `PowerPinRail` and `PowerPinVolts` rows); unused pads `NoConnect`. A 2 × N header standing for an edge connector keeps each letter opposite its number (pad 2n − 1 the n-th number, pad 2k the k-th letter).
- **A monitor** (`VIDEO` composite, `MONITOR` separate drives): no Part logic; the Session and `bw run --tv` find the connector by name and build the TV's consumer on its Nets (`TvConsumer`, `TvInput`, `TvSync`); a video active low is inverted in the consumer. The TV's controls (P6f: position, tone, power, underscan; `src/view/tv_controls`) are UI only: the Tv device paints the same frame whatever they are, so tests read `completedFrame()` unaffected; a picture shown by the UI starts its lines at the sync edge, and a real monitor hides the first 10 µs (Tv columns 0–80) and rows 0–27, so a new Machine's picture belongs after them.
- **A key matrix** (`MATRIXKB`): the Part owns one `SwitchContact` a key, which the builder joins to the Board's `SwitchNetwork` between its row and column Pins' Nets (`wireSwitches`): ghosting and the matrix's faults on the Board side come for free. Held from the UI (`setHeld` + a wake), typed in simulation time from an SPSC queue (a press held 40 ms then released 40 ms, longer than a scan), its pins `sampled` (a row's change must not wake the Part and disturb its own timing); the scripted press published in an atomic for the window to draw.
- **A key matrix that drives its columns** (`MEMBRANEKB`, the ZX80's keyboard, P5x `cf1630e`): when the rows are the CPU's address lines and the real keyboard has a diode a row, the Part is a plain Component, not switch contacts: the rows are `Input`s that wake it (it must answer inside an `IN`), the columns `PinKind::OpenCollector` outputs pulled low while a held key's row reads `Zero`, else released to the Board's pull-ups. A floating or X row does nothing (the diode needs a low). It costs nothing until a key is held.
- **A second keyboard of either kind** implements `KeyMatrix` (`src/parts/key_matrix.hpp`: kind, key count, SHIFT key, held keys, `type(text)`, the scripted press) over a `PressQueue` (`press_queue.hpp`: the SPSC queue and the hold/gap timing, `step(now)` returning the delay to wake after); the Session (`typeText`, `matrixKind`), `bw run`/`bw_ui --type` (`Typing::text`, queued whole at `start`) and the window and capture (`MatrixCapture::kind`) then need only the kind's key table, key map and look. The hold and gap come from the ROM's scan: read the debounce (the ZX80 wants two matching frames, then five empty ones: 60 ms down, 120 ms up).
- **Paste as a listing** (`Zx80Presses`): when the firmware types a keyword a key, the paste goes through a tokenizer that knows where the editor expects a keyword (the ZX80: a line's start, after THEN) and types the rest by character; it is pure and tested on its own, and `type(text)` takes the text whole so the words are seen.
- **The window's look by kind** (`matrix_keyboard_window.cpp`): one cap loop (buttons, latch, the Session's held keys) over the kind's caps (`Zx80Caps`, `Bw2001Caps`) with a draw function each; the ZX80's membrane after Searle's overlay (black panel, blue caps, white keywords above, yellow shifted legends, arrows drawn, graphics as a mosaic).

## Gotchas

- A device that takes the whole PC keyboard (the ASCII keyboard) needs a capture mode in `bw_ui` (`src/ui/keyboard_capture.cpp`): always on, its window out or put away, but while a text field is edited (P6o: every key goes to the Machine but Tab, `` ` `` and Cmd combinations, which `main.cpp`'s event loop takes first; a new device that takes keys sets its `on` in `main.cpp`'s `applyKeys`; no gold, no click to take the keys); SDL key and text events taken before ImGui sees them, key-ups always seen and passed on so no key stays held; PC keys drawn by what they type, not where they sit (any PC layout); Ctrl codes from the shifted key (`SDL_GetKeyFromScancode` with Shift); `SDL_StartTextInput` kept on while capturing; a banner drawn with or without a Board.
- PC typing into a slow Machine (BW-2001 at 0.23×): queue the press in simulation time rather than hold the key for as long as the PC key is down; a quick tap would last about one scan. Paste is the same queue (Cmd/Ctrl+V while the window captures, `SDL_GetClipboardText`).
- The keycap font has no arrow glyphs: draw ←, ↑ and the CRSR arrows with ImGui primitives.
- In `bw_ui`, a scripted input (`--press`, `--type`) must not act in the first frame after a power-on: `status.simTime` is still the previous run's.

- A Puzzle that unpowers the device cracks its supply Trace: ask for the device's `VCC` pad as a leaf of `VCC` in the layout (045 Dead knob).
- On a damaged Board the Nets are named from the Copper: compare pin Nets (`PinNet`) rather than design Net names in Puzzle tests.
