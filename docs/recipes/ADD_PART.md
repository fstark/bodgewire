# Recipe — Add a chip Part

A new IC in the catalogue (e.g. 74LS90, 74LS47). For an on-board LED, digit or button, see [ADD_BOARD_DEVICE.md](ADD_BOARD_DEVICE.md) instead.

Tri-state buffers in groups, with data, enable and disable delays: `a52b167` (74LS244). ## Which kind

- **Gate package** (only independent gates, no state): add a pin-name array, a `GateUnit` array and a `GatePackageSpec` row in `src/parts/gate_package.cpp` (the row ends with `&EvaluatePackage<its units, its delays>`), then `&CreateGatePackage<"74LSxx">` in the catalogue. No new class.
- **ROM** (2716, 2513, 2316B): in `src/parts/rom.cpp`, the pin arrays (pin names, address pins low bit first with their delays, data pins, enables with their delays), a `RomLayout` built from them with the float delay, and a `RomSpec` row ending with `&EvaluateRom<its layout>`; then `&CreateRom<"NNNN">` in the catalogue. No new class. The contents come from `contents=<file>` ([ROM_PARTS.md](../p4l-rom-parts/ROM_PARTS.md) for the `.rom` format), or a raw dump of exactly the ROM's size when the file ends in `.bin`; `PartPinNames` reads the names from the spec. A ROM whose chip-select polarities are set in the mask (2316B) has `selectable` in its row: `select=` (one `L` or `H` per enable, in the spec's enable order) is then required, and its pins drop `_N`.
- A ROM with mask-set selects takes `select=` with one letter per enable; `CreateRom` builds its messages from the number of enables (the 2316B's three, the 2332's two).
- **Memory chip** (RAM, ROM, or a chip holding one): keep the words in a `RomBlock` or `RamBlock` (`src/parts/memory_block.hpp`: power-on draws, stuck bits) and implement `MemoryCells` (`wordCount`, `dataBit`, `stick`), so `fault cell` and `fault column` reach it. A chip with several memories names them in `memories()` (the 6530's `rom`, `ram`); the Puzzle line then needs the name (ADD_PUZZLE).
- **Chip with state or special logic**: a new `Component` subclass `LsNN` in `src/parts/lsNN.{hpp,cpp}`, registered with `&CreateChip<LsNN, "74LSNN">`.
- **Peripheral with many modes** (6522): its logic as a core with no simulator types (`Mos6522Core`: `rise(inputs)`, `read`, `write`, `fall`, `outputs`), tested cycle by cycle, each rule checked against a mutation; the Part around it only samples the Pins at the clock edges and drives what changed.
- **CPU** (6502): the instruction core apart from the Pins, as P5c ([MOS6502_DESIGN.md](../p5c-6502/MOS6502_DESIGN.md)): a core class with no simulator types (`bus()` for the cycle in progress, `step(data)` to end it, input levels set before each step), checked cycle by cycle against public conformance data (`tests/data/6502/`: a subset committed, the full sets fetched by a script into git-ignored `external/`, their cases `SKIP` without it); then a `Component` that runs the core on the clock's edges, every other input `sampled`. Hand-written cases cover what the data does not (interrupt timing, reset); each is checked to fail on a mutation of the rule it tests. A CPU whose bus cycles last several clocks (Z80, P5s, [Z80_DESIGN.md](../p5s-z80/Z80_DESIGN.md)): the core works one M-cycle at a time (`bus()` gives its kind, address, data, refresh, and an `Internal` cycle for internal T-states, so a data-dependent one is decided after its read), written as a resumable function: each instruction straight-line code, each cycle a `case __COUNTER__` resume point of one switch (never inside a nested switch; decoding by `goto`); the Part sequences each kind's T-states, latches the data at its edge, and calls `setInt` and `step()` at the cycle's last rising edge (or at the data edge when that comes later), so the core sees INT as the pins had it at the last T-state; bus grant and reset live in the Part only. The conformance runner expands each M-cycle into the data's own per-T-state sampling (Harte's "simplified" Z80 sampling), separately from the Part. Test data whose instruction set Harte leaves out (prefix chains, `ED` holes) gets hand cases. A fetch script whose file names have spaces writes them with `_`; a Python script that imports a sibling sets `sys.dont_write_bytecode`.

## Rules and gotchas

- Pin names: datasheet names, active-low suffix `_N` (`CLR_N`, `LOAD_N`); gates `1A`, `1Y`; unused pins `NCn` with `PinKind::NoConnect`.
- Shared data pins (a RAM's `IO`, a transceiver): `PinKind::Bidirectional`. The pin is a Driver and a reader of its Net, starts released (Z) at power-on, and its chip is evaluated when its own drive changes the Net. MOS chips (RAM) read inputs with `ctx.readBit` / `ctx.readBitBefore` (X → random bit); a chip whose pins are MOS goes in `kMosSignals` in `tests/parts/catalogue_test.cpp`.
- NMOS port pins with their own pull-up (6530 `PA`, `PB`, 6520, 6522): `PinKind::PullUp`. It drives 0 (and X) at `DriveStrength::Port` and 1 `Weak`: its 0 beats a pull-up resistor and another port's 1, and loses to any output's 1, as an LS output's high (tens of mA) beats an NMOS port's sink (about 2 mA; P5q: after the PET's killer poke the VIA's `PB5` drives 0 against the video's gate, and the gate wins). Nothing else on the Net reads 1, not floating; it reads its Net. A bus transceiver's pin with its own termination (MC3446) is the same kind. It starts released at power-on (no random draw); set it in `powerOn`. Drive it only when its value changes.
- Open-collector outputs: `PinKind::OpenCollector` (needs a pull-up on the Board); drive 1 to release (`DriveOf` maps 1 to no drive).
- Falling-edge clocks (74LS90, 74LS93, 74LS107): `ctx.fell(pin)`; leave the pin's `risingEdgeOnly` false, so it is evaluated on both edges.
- Sampled inputs (the `D`s of the 74LS74 and 74LS175): `sampled = true` on a Pin tells the kernel that its changes never wake the chip, which spares an evaluation each time the data moves between clock edges. Only for a Pin that `evaluate` reads when another Pin acts and at no other time (`readBefore` at the clock edge). A Pin that acts by itself must stay unmarked, or the chip misses its changes without any error: an asynchronous clear, preset or load, an enable, the parallel inputs of a 74LS165 (transparent while `SH_LD_N` is low), anything an output follows directly. Check it in the Part's test (`pins[…].sampled`).
- Power Pins not at the DIP corners (74LS90, 74LS93: `VCC` pin 5, `GND` pin 10): add the Part to `kOffCornerPower` in `tests/parts/catalogue_test.cpp`.
- X on a control input makes the affected state X; never invent a 0/1.
- No zero delays, no delta cycles: every `drive` has a datasheet delay.
- Hot path: `evaluate` must not allocate (use `std::array`, no `std::vector`/`std::string`).
- Specialised evaluation (P5b): a Part family written once behind a spec table (gate packages, ROMs) pays for its generality at every evaluation: loops over spans of run-time length, a `switch` per gate, delays fetched from the row. The cure keeps one source: the evaluation is a function template whose parameter is the row's `constexpr` data (`template <const auto& Units, const Delays& PartDelays>`, `template <const auto& L>` for a ROM), each spec row holds a pointer to its instance, and the class's `evaluate` is that one call. The compiler unrolls the loops and folds the constants. `EvalContext` and the Part's tests stay as they are. Worth it only for a Part that a profile shows hot, and only for a spec-table family: a hand-written class (74LS157, 74LS244) already has its Pins and delays as constants, and rewriting its logic gained nothing measurable (P5b, ideas 4.3 and 4.4); its cost is the `read` and `drive` calls.
- Several units in one Part (74LS107): test them with `GENERATE`, not `SECTION`s inside a loop (Catch2 sections in loops are unreliable).
- `-Werror` includes unused private fields. Run `clang-format` on C++ files only, never on `CMakeLists.txt`.
- A Part acting by itself after power-on with no inputs (`POR`): set the output in `powerOn` and schedule the change from the power-on evaluation with one `drive` whose delay is the time (exact, no wake needed); nothing evaluates it again.
- A Part with a required parameter (`OSC freq=`, `PADDLE`, `POR time=`, `6530 mask=`): `catalogue_test.cpp` (chip pinouts) and `PartPinNames` in `src/manual/manual.cpp` build every Part and must pass one; without it `PartPinNames` returns nothing and the datasheet's pins go unchecked, silently (add a size check in `tests/manual/manual_test.cpp`).
- A Part with a file parameter (ROM and 6530 `contents=`): the catalogue test, the footprint test and any test that builds every Part must pass one (`tests/data/empty.rom`); `PartPinNames` cannot build it, so it returns the names from the spec (ROM) or a static `Pins()` (6530); paths resolve against the netlist's directory (`ResolveContentsPaths`), so a test that parses a netlist itself calls it too.
- A new package: copy the footprint from the installed KiCad into `boards/footprints/` unchanged and add a `kFootprints` row before any catalogue row uses it (the footprint test loads every catalogue package). A DIP-14/16-wide package (DIP-18, DIP-20) is also a grid package: add it to `IsGridPackage` in `src/board/placer.cpp`. A package wider than DIP-16 (DIP-24) has no slot in the chip grid of `bw place`: the Machine's `.place` must place it with a rule (`row`, `edge`).
- A second ground pin (the 6502's two `VSS`): name it `GND2`; `PowerPinRail` puts it on `GND` for the builder and `PowerPinVolts` gives 0 V. Another extra power pin needs a row in both.
- A P-MOS chip without a `GND` pin (2524, 2518: `VCC` and a negative supply): the negative supply pin is `NoConnect` with the chip's MOS family, and the Part goes in `kNoGround` (and `kMosSignals`) in `tests/parts/catalogue_test.cpp`. The power check needs only `VCC` on its rail.
- Dynamic storage (2524): keep the time of the last clock edges and fade the contents lazily at the next one, once (to a level the datasheet's physics suggests, stated in its file), not again until the clocks run; no wake is needed: the contents only show through outputs that move on a clock, and an output frozen with its clocks looks the same on the board as a faded one.
- Speed grades (the 2114, 2114-3, 2114-2): a parameter with the grade's access time (`access=300ns`), refused outside the grades, the default the slowest; a Machine whose real board works only with faster parts (the PET's video path: P5q) names the grade. Datasheet maximums otherwise.
- Old MOS datasheets (2513, 2518 pp. 81–85, 2524 pp. 93–97) are in the 1972 Signetics MOS data book on bitsavers; EPROMs (2716) publish only maximum delays: use them and say so.
- Motorola's interface parts (MC3446) are in the 1979 Motorola Interface Integrated Circuits data book on bitsavers (`components/motorola/_dataBooks/`); find the page with `pdftotext` and render it.
- TI datasheet PDFs can't be fetched: use known typical values and say so in the commit. The TI 1976 TTL Data Book on bitsavers (`components/ti/_dataBooks/`) has the plain-TTL parts (74100, 74154, 74177); MOS and Rockwell peripheral sheets are on 6502.org (`documents/datasheets/`).
- A real ROM (the user's own dump) in a test: never committed unless the user decides so (the PET's character ROM was, 2026-11-15); kept in git-ignored `external/roms/`, found through `ExternalRom` (`tests/netlist/external_rom.hpp`), the case `SKIP`ped without it, its files listed with their SHA1s in `tests/data/pet_roms.md`.
- An output that pulses for one cycle (a 6520 or 6522 handshake strobe) needs each edge's delay under half a cycle, even when the data sheet allows more: drives are inertial, so a second edge scheduled when the first applies replaces it. Say the delay is assumed.
- Test benches for a new chip: `tests/parts/chip_bench.hpp` (one chip, a Stimulus on every input) for TTL; `tests/parts/bus_bench.hpp` (a scripted 1 MHz bus: register reads and writes, selects, reset, outside drives on the other Pins) for a bus peripheral.
